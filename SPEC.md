## 0. Сводка спецификации (актуальная)

### 0.1 Продукт

- **Total Commander** над Google Drive: веб-приложение (GAS + clasp), **две панели**; drag-and-drop — в спецификации, **в коде ещё нет**.
<!-- OLD: «две панели, drag-and-drop» как будто уже есть — DnD не реализован -->
- **Файлы** — одна **плоская папка** на Drive (человеческие имена, дубликаты имён допустимы).
- **Дерево, метаданные, права** — Google Таблица (7 листов + `DocumentProperties`).
- **Быстрота UI**; медленные операции (импорт, Drive, очистка корзины…) — **в фоне / Jobs**; прогресс Jobs — **строка статуса** (`N/M`); splash — §0.2 / §2.8.

### 0.3 Права

- **Два слоя:** роль входа (§14.4) + права на объект (§4).
- **Роли входа:** Пользователь | Менеджер | Управляющий (один = владелец таблицы).
- **Права на объект:** нет прав | читатель | комментатор | редактор.
- Листание — **все видят всё**; открытие — по правам; на Drive — **временный доступ**, сброс **04:00 Москва**.
- **Drive vs каталог:** на реальных файлах Drive по умолчанию только **владелец каталога** (технический фон, в ACL/отчётах не показываем). Истина прав — в каталогизаторе. Смена прав → **только таблица**; на Drive доступ выдаётся **в момент открытия**, если у открывающего есть право.
- **Модель ACL (вариант A, согласовано 2026-07-27) — §4.4a:** лист `ACL` хранит **отклонения** относительно матери: знак `+` / `−` + principal + уровень. Эффективные права = эффективные(мать) ⊕ отклонения(объект); при разборе дельт путь до корня (или кэш эффективных у матери). Корень — **базовый** ACL (не дельты). `acl_*` в Tree/Files — только **кэш эффективных** ярлыков для UI (без `+/−` в тексте).
<!-- OLD: **Явный ACL на каждом** файле/папке (лист `ACL`). Наследование — только при **записи** (копия с родителя / `setObjectAcl` папки → поддерево / create/import/move). **Сироты** (объект без ACL) — материализуются от родителя **при старте snapshot**. -->
- **Группа в столбцах** = один ярлык `#Имя`; состав группы разворачивается при **открытии** / операциях, где нужны конкретные редакторы.
- **Кэш UI:** `Tree`/`Files` колонки `acl_editors|acl_commenters|acl_readers` (schema **0.4**+) — снимок **не** пересчитывает наследование на каждый объект; кэш = **эффективные** ярлыки (пересчёт при записи ACL / заполнении пустых колонок).
<!-- OLD: **Кэш UI:** `Tree`/`Files` колонки `acl_editors|acl_commenters|acl_readers` (schema **0.4**) — снимок **не** пересчитывает наследование; после перехода на дельты — кэш **эффективных** (пересчёт при записи ACL). -->
- **Переназначение прав папки** → эффективные права папки как задано в UI; в `ACL` не-корень пишет **дельты относительно матери**, корень — базу; **рекурсивный сброс всех отклонений** у детей + кэш поддерева (§4.4a). Смена прав файла/подпапки → не меняет родителя.
<!-- OLD: **Переназначение прав папки** → новый базовый ACL папки + **рекурсивный сброс всех отклонений** у детей (§4.4a). Смена прав файла/подпапки → не меняет родителя. -->
- Персональные права **> группа**; среди групп — **максимум**. Конфликт `+` и `−` у одного principal на одном объекте/уровне — ошибка целостности; при разборе **`−` сильнее**.
- **Утверждён:** эффективные editor → commenter (и унаследованные, и из `+`); далее editor не выдаётся (§7).

- **Отображение в каталоге** (навигация, появление файла после добавления) — **мгновенно**, это критический путь UI.

## 2. Интерфейс

| Параметр | Решение |
|---|---|
| Платформа | Веб-приложение |
| Компоновка | Две панели, логика визуализации как в Total Commander |
| Манипуляции | Перетаскивание мышью (drag-and-drop) между панелями и внутри них |
| Строка статуса | Внизу окна — **два ряда** §2.6: командный (кнопки + подсказки F-клавиш) и статусный (сообщения, прогресс) |

### 2.1 Две панели (как Total Commander)

- **Обе панели одинаковы** по возможностям — симметричные независимые навигаторы.
- Каждая панель показывает **свою текущую локацию** и навигируется **независимо** от другой.
- **Локация панели** может быть:
  - **виртуальная папка каталога**, или
  - **место на Google Drive** вне каталога (для импорта и сравнения). <!-- OLD: см. ниже -->
- **Обе панели всегда** показывают **место в каталоге** — **корень** или **одна из виртуальных папок** (в т.ч. корзина).
- Импорт с Drive / с компьютера — **отдельный сценарий** *(TBD: диалог, drag-and-drop в панель и т.п.)*, не через навигацию по внешнему Drive в панели. <!-- OLD: см. §2.5 -->
- **Копирование / перемещение / drag-and-drop** — **между панелями** и **внутри панели**, по тем же правилам, что в Total Commander.
- Типичный сценарий: одна панель — **каталог**, вторая — **источник на Drive** или **другая папка каталога**. <!-- OLD: обе панели — только каталог; см. §2.1 -->
- Типичный сценарий: **две папки каталога** в разных ветках (копирование/перемещение F5/F6).
- После **первого входа** (и по умолчанию при открытии приложения) **обе панели** показывают **корневую виртуальную папку** каталога (§15.2).

### 2.2 Список папок и файлов в панели

#### 2.2.1 Порядок и открытие

2. Когда файл **открывали**.

### 2.7 Скорость навигации по каталогу

**Цель:** листание панелей — **мгновенно** (§1.2); задержка допустима на **старте** и на **записи** операции (ограничение GAS).

## 3. Хранение данных

### 3.1 Google Drive

- Все файлы каталога лежат в **одной физической папке** на Google Drive.
- Папка принадлежит **владельцу каталога**.
- Внутри папки **нет подпапок** — только «плоский» список файлов.
- Имена файлов на Drive — **исходные «человеческие» названия**.
- Google Drive **не требует уникальности имён** в одной папке: у каждого файла свой `file_id`.

### 3.2 Google Таблица

- **Виртуальное дерево папок** хранится в Google Таблице.
- **Служебная информация** (метаданные, права, статусы) — в Google Таблице.
- Связь записи каталога с файлом на Drive — через `file_id`.

### 3.3 Один экземпляр каталога

- **Один каталогизатор = одна Google Таблица** + **одна плоская папка** на Drive.
- Несколько независимых каталогов в одной таблице **не предусмотрено**.

## 4. Права доступа

### 4.1 Общие принципы

- Каталогизатор — **единственный источник истины** по правам доступа.
- На Drive по умолчанию доступ к каждому файлу имеет **только владелец каталога**.
- Права задаются **отдельно для каждого файла** и **отдельно для каждой папки** (виртуальной).
- Уровни прав (как в Google Drive):
  - **нет прав**
  - **читатель**
  - **комментатор**
  - **редактор**

### 4.2 Навигация vs открытие

- При **листании панелей** (без открытия файла) пользователь **видит все файлы и папки** каталога.
- Ограничение по правам срабатывает при **открытии** файла.

### 4.3 Выдача доступа на Drive

- При **открытии** конкретного файла пользователю выдаётся временный доступ на Drive с уровнем, соответствующим его правам в каталогизаторе.
- **Ежедневно в 04:00** все ранее выданные доступы **обнуляются** (отзываются).
- Часовой пояс сброса: **Москва (UTC+3)**.

### 4.4 Наследование прав

1. **Смена прав папки** → все вложенные файлы и подпапки **получают те же права** (включая объекты, у которых права были заданы индивидуально — они **перезаписываются**).
2. **Смена прав конкретного файла или подпапки** → **не влияет** на права родительской папки.

**Хранение (согласовано 2026-07-19) — до перехода на §4.4a:**

- На **каждом** файле и папке в листе `ACL` хранятся **явные** записи (не «дыры» с чтением родителя на лету).
- Правило §4.4 применяется при **записи** (create / import / move / `setObjectAcl` папки / материализация сирот).
- **Сирота** (объект без строк ACL) при `getCatalogSnapshot` → копируем ACL от ближайшего родителя и пишем в таблицу + обновляем кэш `acl_*`.
- В UI-столбцах группа = **один** principal `#Имя`; разворот членов — при открытии файла и при проверках «конкретный редактор».
- Кэш `acl_*` в Tree/Files обновляется при любой записи ACL (чтобы навигация оставалась мгновенной).

### 4.4a Отклонения ACL (вариант A) — канон с 2026-07-27

**Смысл:** не дублировать полный список на каждом объекте; хранить относительно матери **добавки** и **исключения**.

**Формула:**  
`эффективные(объект) = эффективные(мать) ∪ {записи delta=+ } \ {записи delta=- }`  
(по каждому уровню editor/commenter/reader; персональное > группа; среди групп — max).  
У **корня** матери нет → записи ACL = **база** (`delta` пусто/`base`).

**Хранение (вариант A):**

| Слой | Что хранит |
|---|---|
| Лист `ACL` | Истина: principal + `permission_level` + **`delta` ∈ {`+`,`−`}** (не-корень); корень — база |
| `Tree`/`Files`.`acl_*` | Только **кэш эффективных** ярлыков для панелей/выгрузки UI (**без** префиксов `+/−` в тексте) |

Отклонён вариант B: хранить `+/−` только в текстовых `acl_*` (парсинг, хрупкость, дубль с `ACL`).

**UI / выгрузка отклонений:** в отчётах можно показывать `+Имя`, `-Имя`, `+#Группа`, `-#Группа`. В панелях — по-прежнему эффективный список.

**Правила записи:**

1. Create / import / move ребёнка → по умолчанию **нет строк отклонений** (эффективные = как у матери); кэш `acl_*` = от матери (с учётом утверждённости файла).
2. Расширение прав → строки `delta=+`. Сужение относительно матери → строки `delta=-` (точечно; «только добавками сузить нельзя» без `-`).
3. **Переназначение прав папки** → UI задаёт **эффективные** права папки; в листе не-корень пишет **дельты относительно матери** (корень — база); **рекурсивно удалить все ACL-отклонения** всех потомков + пересчитать кэш `acl_*` в поддереве. *(«База для поддерева» = дети без отклонений наследуют эту папку; абсолютные строки базы — только у корня.)*
<!-- OLD: 3. **Переназначение прав папки** → записать новый **базовый** набор на эту папку (как для узла, чьи эффективные задаются заново) + **рекурсивно удалить все ACL-отклонения** всех потомков (подпапки и файлы) + пересчитать кэш `acl_*` в поддереве. -->
4. Смена ACL файла / одной подпапки → не меняет родителя; потомков у файла нет.
5. Конфликт: один principal с `+` и `-` на одном объекте и уровне — **ошибка целостности**; при разборе **`−` сильнее**. Занести в отчёт целостности (§17).
6. **Утверждённый файл:** при вычислении эффективных / открытии все `editor` → `commenter` (унаследованные и из `+`); в дельтах editor может оставаться, demote — на этапе эффективности.

8. Миграция со старых полных ACL **не нужна** (тестовый каталог; права можно сбросить вручную перед включением кода).

**Проверка при открытии:** можно идти путём к корню по дельтам **или** взять кэш эффективных матери + применить дельты ребёнка (если кэш матери гарантированно свеж после записей).

### 4.5 Кто назначает права на объекты

- **Управляющий** задаёт права на **все файлы и папки в корне** каталога (верхний уровень виртуального дерева).
- **Менеджеры** могут **назначать права** на объекты **внутри своих папок** — в тех виртуальных папках, где они управляют доступом *(TBD: «своя папка» = папка, где у менеджера право «редактор» на объект)*. <!-- OLD: см. ниже -->
- **Менеджеры** могут **назначать права** на объекты **внутри своих папок**. **Своя папка** — виртуальная папка, где у менеджера есть право **редактор** на объект (§4). <!-- OLD: см. ниже -->
- **Менеджеры** могут **назначать права** на **саму свою папку** (где они **редактор**) и на объекты **внутри неё** (вложенные папки и файлы). **Своя папка** — виртуальная папка, где у менеджера право **редактор** на объект (§4). <!-- OLD: см. ниже -->
- **Менеджеры** могут **назначать права** на **любую папку и подпапки**, где у них есть право **редактор** на объект (§4) — не только на одну «свою» ветку, а на **каждую** такую папку в дереве.
- При назначении прав действуют те же правила **наследования** (§4.4).

## 7. Статус «утверждён»

Файл может иметь статус **«утверждён»** (в UI — **«Подписать»**).

При установке статуса «утверждён»:

1. Все пользователи, у которых было право **редактор**, получают право **комментатор** (на уровне ACL каталога).
2. После утверждения **никому** не выдаётся право **редактор** на этот файл (в том числе при наследовании прав от папки и при явной выдаче).
3. Файл **больше нельзя редактировать** (нет editor); **чтение и комментирование** по-прежнему возможны по правам.

## 9. Импорт файлов

### 9.1 Копирование vs перемещение

- Режим импорта (**копирование** или **перемещение**) выбирает **пользователь** для каждого файла или для **папки целиком** (со всеми вложенными файлами).
- **Копирование** — оригинал остаётся в источнике; в плоскую папку каталога попадает копия.
- **Перемещение** — оригинал исчезает из источника; файл оказывается в плоской папке каталога.

### 9.2 Владелец файла

- Если у импортируемого файла **другой владелец** (не владелец каталога) — доступен **только режим копирования**.
- Цель: **все файлы в каталоге принадлежат владельцу каталога**.

### 9.3 Пакетная обработка

- Нужна **пакетная обработка** для **массового импорта** старых файлов.

### 9.4 Пользователи при импорте

- При импорте файла **пополняем список пользователей** каталогизатора: добавляются те, у кого **были доступы** к импортируемому файлу (на Drive до импорта).
- Новым пользователям при импорте автоматически назначается роль входа **Пользователь** (§14.4).
- При импорте переносим **только права** на объекты (читатель / комментатор / редактор). Статусы вроде **«утверждён»** при импорте **не переносим**.

### 9.8 Права при импорте папки (ускорение)

- Для **ускорения импорта** права **не копируются по каждому вложенному файлу** отдельно.
- Права берутся **с импортируемой папки** (источник на Drive) и задаются на **корень** импортированной ветки в каталоге.
- Всё **внутри** наследует права от этой папки по правилам §4.4.
- Если у вложенных файлов на Drive были **разные права** — это **осознанное упрощение**: внутри ветки права **выравниваются** по корню импортированной папки.

## 13. Операции файлового менеджера

### 13.1 Базовые операции (v1)

В первой версии поддерживаются все операции:

- **Копирование** — между виртуальными папками (и между панелями). На Drive создаётся **вторая физическая копия** файла (не ярлык, не общая ссылка).
- **F5 производительность (2026-07-27):** запись Tree/Files/ACL — **batch**; ACL новых объектов — один проход листа; UI после sync — **локальный патч** (`created`). Если в операции **≥ 2 файлов** — очередь Jobs `copy_catalog` (сначала pending-строки Files + папки Tree + ACL; воркер — `makeCopy` чанками); статус `Копирование: N/M`; по `done` — reload снимка.

- **Перемещение** — между виртуальными папками.
- **Переименование** — изменение отображаемого имени в каталоге *(TBD: меняется ли имя файла на Drive)*. <!-- OLD: см. ниже -->

- **Удаление** — перенос в **корзину** (см. §13.2).
- **Удаление в корзину (F8)** — только **Менеджер** или **Управляющий** + право **редактор** на **папку**, где лежит объект (§14.6).

### 13.2 Корзина

- **Корзина** — **особая виртуальная папка** в каталоге. Реализация: **системная папка в `Tree`** (§3.5).
- Корзина **видна всем** в списке папок при навигации (§3.5).
- При «удалении» файл **перемещается в корзину** в дереве каталога.
- Статус **«утверждён»** при этом **сохраняется** (§7.1).
- Файл **не удаляется физически** с Google Drive.
- Удалять в корзину могут только **Менеджер / Управляющий** при праве **редактор** на соответствующую **папку** (§14.6).

### 13.3 Восстановление из корзины

**Решение:** отдельной функции **«Восстановить»** **нет**. Возврат файла/папки из корзины — обычное **перемещение F6**:

1. В **активной** панели открыть **корзину** (`__TRASH__`).
2. В **неактивной** панели открыть **целевую** виртуальную папку.
3. Выделить объект в корзине → **F6** (или кнопка «F6 Перем.»).

Технически — тот же `moveCatalogItems`; проверки §14.6–14.7 (редактор на исходной папке-корзине и на целевой).

## 14. Вход в приложение и роли

> **Доступ к функциям приложения** определяется **только тремя глобальными ролями** (ниже). <!-- OLD: см. §14.4 — «роли входа» -->
> Права на конкретный файл/папку (§4) — **отдельный слой**: уровень доступа к объекту и выдача прав на Drive при открытии. <!-- OLD: уточнено в §14.3 -->

### 14.1 Терминология (чтобы не путаться)

| Термин | Что означает |
|---|---|
| **Роли входа** | **Пользователь**, **Менеджер**, **Управляющий** — кто какие **функции приложения** может выполнять (§14.4) |
| **Права на объект** | **нет прав / читатель / комментатор / редактор** — доступ к **конкретному файлу или папке** (§4) |

Слово **«редактор»** в §4 — это **право на объект**, не роль входа. Роль входа **«Менеджер»** — другое.

### 14.2 Аутентификация

- Вход в веб-приложение — по **авторизации**: **email** и **пароль**.
- Email **заранее внесён** в список каталога.
- *(TBD: хранение паролей; связь email с Google-аккаунтом при открытии файла на Drive.)* <!-- OLD: см. ниже -->

**Вход через Google-аккаунт (OAuth):**

- Отдельного пароля каталога **нет**.
- Пользователь авторизуется **Google-аккаунтом** в браузере.
- Каталог проверяет: email из Google-сессии **заранее внесён** в список пользователей → назначается **роль входа** (§14.4).
- Для **открытия файлов** на Drive пользователь должен быть залогинен в **тот же Google-аккаунт** — на него выдаётся временный доступ (§4.3).

### 14.3 Два слоя доступа после входа

1. **Роль входа** — какие **функции каталогизатора** можно **запускать** в приложении (штатные операции, служебные функции). <!-- OLD: см. §14.5 -->
2. **Права на файлы и папки** (§4) — **работа с файлами** после входа: открытие, уровень доступа на Drive, наследование, группы, «утверждён» и т.д.

### 14.4 Три роли входа

| Роль входа | Функции приложения |
|---|---|
| **Пользователь** | Вход; просмотр списков папок и файлов; **открытие** файлов (с учётом прав на объект — §4) |
| **Пользователь** | Вход; просмотр списков папок и файлов. **Не запускает функции каталогизатора** (копирование, перемещение, импорт, управление правами и т.п.). **Работа с файлами** — только в соответствии с **правами на объект** (§4): открытие и уровень доступа на Drive. <!-- OLD: см. строку выше и §14.5 -->

### 14.5 Роль «Пользователь» и права на объект

- **Пользователь** **не может запускать** функции каталогизатора (штатные и служебные операции в UI).
- **Работа с файлами** — **только по правам на объект** (§4): открыть файл, получить на Drive уровень **читатель / комментатор / редактор** в соответствии с выданными правами.

### 14.6 Роль «Менеджер» и права на объект

- Штатные операции может выполнять только **Менеджер** (или **Управляющий**).
- Дополнительно для каждой операции нужны **редакторские права на объект** (§4) — на **папку**, где происходят изменения, и при необходимости на **файл**.
- Без права **редактор** на соответствующую папку/файл операция **недоступна**, даже при роли «Менеджер».
- В т.ч. **удаление в корзину (F8)** — только Менеджер/Управляющий + **редактор** на **папку** объекта.

### 14.8 Управление пользователями и ролями входа

- **Добавлять пользователей** в каталог и **назначать роли входа** могут: **Управляющий** и **Менеджер**. <!-- OLD: см. ниже -->
- **Управляющий всегда один** — это **владелец каталога** (§3.1). Роль **не назначается** другим пользователям.
- **Управляющий** может добавлять пользователей и назначать роли **Пользователь** и **Менеджер**.
- **Менеджер** может добавлять пользователей и назначать роли **Пользователь** и **Менеджер** (роль **Управляющий** — только у владельца каталога).

**Пользователи (`Users`):**

- Ключ — **email** (не меняется).
- Поле **отображаемого имени** (`display_name`) — можно менять; в списках каталога и в окне ACL показываем **имена**, не email.
- Роли при назначении: только `user` / `manager`. Роль **Управляющий** не назначается и не снимается через UI.
- **Удаление** пользователя: убрать строку из `Users` + все членства в `GroupMembers` + все записи `ACL` с этим email. Разрешено Менеджеру и Управляющему. Управляющего удалить нельзя.

**Группы (`Groups` / `GroupMembers`):**

- Имя **уникально**; в ACL — префикс `#имя`. Переименование меняет только отображаемое имя (состав и `group_id` без изменений).
- Участники — **только** пользователи из `Users` (чек-боксы в UI).
- Смена состава группы **не переписывает** ACL объектов: эффективные права пересчитываются при отображении / открытии / операциях.
- **Удаление** группы: удалить `Groups` + `GroupMembers` + **все** `ACL` с этой группой.

**UI:** правка в модальном окне. Раздел **«Группы»** виден **Менеджеру и Управляющему**; править группы может **только Управляющий** (у Менеджера — только просмотр).

- В списках каталога и окне ACL — **`display_name`**, не email (ключ в данных по-прежнему email).

### 14.7 Копирование и перемещение между папками

- Для **копирования** и **перемещения** между виртуальными папками нужны права **редактор** на **обе** папки: **исходную** и **целевую**.
- Цель: **не допустить** ситуации, когда доступ к «секретному» файлу получит пользователь, которому права **не выдавались** (через перенос файла в папку с более широкими правами).
- **После перемещения (F6/F8):** явные ACL перемещённого объекта (для папки — **всего её поддерева**) **перезаписываются** правами **целевой (материнской) папки** — те же правила, что §4.4 при смене прав папки. Источник — эффективные/явные записи целевой папки (`resolveInheritedAclRows_`).
- **Корень** виртуального дерева: прав **никому не роздано** (записей ACL нет) — наследовать нечего; после переноса в корень (или в папку без ACL вверх по цепочке) у объекта **пустые** права в столбцах (кроме особых ролей входа Управляющего).

## 15. Инициализация каталога (setup)

### 15.2 Что делает setup

1. Создаёт **листы** и **заголовки** столбцов (§3.4–3.8), если отсутствуют.
2. Создаёт **плоскую папку** на Google Drive (§3.1) → `CATALOG_ROOT_FOLDER_ID` в `DocumentProperties`. <!-- OLD: см. ниже -->
2. **Плоская папка** на Drive **уже создана Владельцем** до setup. В диалоге инициализации Владелец указывает **ссылку** на неё → из ссылки извлекается `CATALOG_ROOT_FOLDER_ID` → записывается в `DocumentProperties` (§3.11).

**Проверки папки (иначе setup запрещён, показываем ошибку):**

- Папка **принадлежит Владельцу** таблицы.
- Папка **пустая** (нет файлов и подпапок).
3. Создаёт **системную папку корзины** в `Tree` (`__TRASH__`, §3.5).
3. Создаёт **корневую виртуальную папку** каталога в `Tree` (верхний уровень дерева; все рабочие папки — внутри неё). *(TBD: имя по умолчанию, например «Каталог».)* <!-- OLD: см. ниже -->
3. Создаёт **корневую виртуальную папку** в `Tree` с **именем**, которое Владелец **задал в диалоге** setup; все рабочие папки — **внутри** неё → `CATALOG_VIRTUAL_ROOT_FOLDER_ID` в `DocumentProperties` (§3.11).
4. Создаёт **системную папку корзины** в `Tree` (`__TRASH__`, §3.5) **внутри корневой** виртуальной папки. <!-- OLD: было п.3 без корня; корзина на верхнем уровне -->
4. Записывает `SCHEMA_VERSION`, `SETUP_AT`, `CONTROLLER_EMAIL` (§3.11).
5. Добавляет **Владельца таблицы** в `Users` с ролью **Управляющий** (`controller`) — §14.8. <!-- OLD: «инициатора» — только владелец таблицы -->
6. Создаёт **триггер** ежедневного **отзыва временных доступов** на Drive — **04:00 по Москве** (§4.3).
<!-- OLD: п.6 «Идемпотентность» — см. §15.3 -->

### 15.3 Setup один раз; миграции при разработке

- В **готовом продукте** setup выполняется **один раз**. Повторная инициализация **не предусмотрена**.
- Если каталог **уже инициализирован** (`SCHEMA_VERSION` и `CATALOG_ROOT_FOLDER_ID` в `DocumentProperties`) — setup **не запускаем**, работаем как обычно.
- При **несогласованности** данных (листы есть, Properties нет или не совпадают) — **ошибка**, работа **блокируется** *(TBD: текст для Владельца)*.
- **Изменение структуры** листов во время **разработки** — отдельная **временная служебная функция** (миграция), **не** повторный setup.

### 19.2 Дерево (`Tree`) — **быстрая**

| Код (черновик) | Ошибка | Предложенный fix |
|---|---|---|
| `TREE_DUP_ID` | Дубликат `folder_id` | Удалить дубль / смержить *(ручной выбор)* |
| `TREE_MISSING_ID` | Пустой `folder_id` | Удалить строку |
| `TREE_BAD_PARENT` | `parent_folder_id` указывает на несуществующую папку | Перенести в корень / корзину / удалить |
| `TREE_PARENT_CYCLE` | Цикл в родителях | Разорвать цикл (parent → корень) |
| `TREE_MULTI_ROOT` | Больше одной папки без родителя / не тот корень | Оставить канонический `CATALOG_VIRTUAL_ROOT`; прочие — под корень |
| `TREE_NO_ROOT` | Нет корневой папки | Создать/восстановить root *(осторожно)* |

### 19.4 ACL (дельты — §4.4a) — **быстрая**, обязательно

| `ACL_BAD_OBJECT` | `object_id` нет в Tree/Files | Удалить ACL-строки |
| `ACL_BAD_TYPE` | `object_type` / `principal_type` / `permission_level` / `delta` вне enum | Удалить или нормализовать |
